=== Minimal UEFI Application

The loader begins as a small freestanding UEFI application.
`\#![no_std]` removes the hosted Rust standard library, while `\#![no_main]` avoids Rust's normal program entry point.
The `uefi` crate's `#[entry]` macro supplies the ABI-compatible wrapper expected by the firmware:

[source,rust]
----
#![no_main]
#![no_std]

use uefi::{entry, Status};

extern crate alloc;

#[entry]
fn main() -> Status {
    loop {}
}
----

This stub proves that the firmware can locate the image, load it, and enter Rust code. Compiling this segment can already generate a bootable lodaer binary.
The loader crate enables the `global_allocator`, `alloc`, and `panic_handler` features of `uefi`, making heap-backed types available while boot services are active.
That allocator must not be used after leaving boot services.

=== Adding Early Diagnostics

The first useful expansion gives the remaining loader work a visible diagnostic channel:

. acquire and clear the GOP framebuffer;
. load and validate `font.psf` from the boot filesystem;
. install a framebuffer-backed logger; and
. stop in a loop after confirming the initialized resources.

[source,rust]
----
#[entry]
fn main() -> Status {
    let fb = graphics::initialize_framebuffer().unwrap();
    fb.fill(color::BACKGROUND);

    let fb_addr = fb.ptr() as *mut u8 as u64;
    let fb_page_num = fb.ptr().len().div_ceil(PAGE_SIZE);

    let font = graphics::parse_psf_font(PSF_FILE_NAME).unwrap();
    let writer = RawWriter::new(font, fb, color::INFO, color::BACKGROUND);
    Logger::init(writer);

    info!("Hello World!!");
    debug!("Framebuffer: address: {fb_addr:#x}, number of pages: {fb_page_num:#x}");

    loop {}
}
----

=== Reading Files from the Boot Volume

Both `font.psf` and `kernel.elf` reside beside the loader on the EFI System Partition.
The file helper opens the filesystem associated with the current image rather than searching arbitrary disks:

[source,rust]
----
pub(crate) fn get_file_data(filename: &'static str) -> Result<Vec<u8>> {
    let fs: ScopedProtocol<SimpleFileSystem> =
        boot::get_image_file_system(boot::image_handle())?;
    let mut fs = FileSystem::new(fs);

    let path = CString16::try_from(filename)?;
    Ok(fs.read(path.as_ref())?)
}
----

UEFI paths use UTF-16, hence the conversion to `CString16`.
`ScopedProtocol` also expresses an important lifetime: the opened protocol is released when the wrapper goes out of scope.
Returning an owned `Vec<u8>` decouples the file contents from the protocol handle, though the vector still depends on the UEFI allocator.
The same helper supplies bytes to the font parser and is also suitable for reading the kernel ELF image.

The loader has a single `LoaderError` enum with conversions for UEFI, filesystem, string-conversion, and PSF failures.
The helpers therefore use `Result` and `?`.
The top-level `unwrap` calls are acceptable during bring-up; a robust loader should replace them with a visible error-and-halt path.

=== Acquiring the Framebuffer

GOP describes a linear framebuffer through its base address, byte size, resolution, scan-line stride, and pixel format.
The loader opens GOP exclusively and translates that description into the type expected by the `framebuf` dependency:

[source,rust]
----
let handle = boot::get_handle_for_protocol::<gop::GraphicsOutput>()?;
let mut gop = boot::open_protocol_exclusive::<gop::GraphicsOutput>(handle)?;

let gop_mode = gop.current_mode_info();
let gop_fb_size = gop.frame_buffer().size();
let (format, bpp) = match gop_mode.pixel_format() {
    gop::PixelFormat::Rgb => (framebuf::raw::PixelFormat::Rgb32bit, 4),
    gop::PixelFormat::Bgr => (framebuf::raw::PixelFormat::Bgr32bit, 4),
    gop::PixelFormat::Bitmask => unimplemented!(),
    gop::PixelFormat::BltOnly => unimplemented!(),
};
----

The real implementation then calls `RawFrameBuffer::new` with the framebuffer pointer and this metadata.
That constructor is unsafe because Rust cannot prove that a firmware-provided physical range is valid for the claimed length or that writes are unique.
The loader establishes those preconditions from the GOP response and keeps a single mutable wrapper.
It currently supports only the common 32-bit RGB and BGR modes; bitmask and blit-only devices need an explicit fallback.

The framebuffer is memory-mapped I/O, not ordinary allocated RAM.
The kernel page tables must map the complete GOP range with suitable cache attributes, and the custom boot protocol must carry both its address and layout.

=== PSF and Early Text Output

PC Screen Font is a compact bitmap-font format consisting of a header followed by fixed-size glyph bitmaps.
PSF1 uses 8-pixel-wide glyphs and a small header; PSF2 records width, height, glyph size, and glyph count explicitly.
Their magic values let the loader distinguish the two versions.
The OSDev Wiki's https://wiki.osdev.org/PC_Screen_Font[PC Screen Font chapter] documents both layouts and glyph rendering in more detail.

Telos only needs the loader-specific part of this process.
`parse_psf_font` reads the file, checks its magic and total required length, and copies the validated header and glyph bytes into page-based storage:

[source,rust]
----
let page_count = total_size.div_ceil(PAGE_SIZE);
let font_address = boot::allocate_pages(
    boot::AllocateType::AnyPages,
    MemoryType::LOADER_DATA,
    page_count,
)?;

unsafe {
    core::ptr::copy_nonoverlapping(
        font_data_ptr,
        font_address.as_ptr(),
        size_of::<PSF1Header>(),
    );
}

let glyph_buffer_ptr = unsafe {
    font_address.as_ptr().add(size_of::<PSF1Header>())
};

unsafe {
    core::ptr::copy_nonoverlapping(
        font_data_ptr.add(size_of::<PSF1Header>()),
        glyph_buffer_ptr,
        glyph_buffer_size,
    );
}
----

This excerpt shows the PSF1 branch; the PSF2 branch applies the same allocation and copy pattern with its larger header.
The temporary `Vec` may be dropped after parsing; the returned `RawFont` points into the page allocation instead.
Marking pages as `LOADER_DATA` does not make them permanently reserved: after `ExitBootServices` they become the operating system's responsibility.
The physical-memory manager must keep these frames allocated for as long as the logger uses them.

Glyph rasterization, cursor movement, color conversion, and the `log::Log` implementation belong to the `framebuf` crate and are intentionally treated as dependency behavior here.
The loader only combines the persistent font with the GOP descriptor and registers the resulting writer:

[source,rust]
----
let writer = RawWriter::new(font, fb, color::INFO, color::BACKGROUND);
Logger::init(writer);
----

This gives the loader a useful diagnostic channel without making rendering the focus of the bootloader.
