=== Minimal UEFI Application

With the image layout in place, the loader can begin as a minimal UEFI application.
Like the kernel, it uses `\#![no_std]`, because Rust's standard library assumes services supplied by a host operating system.
Unlike the kernel, however, it can still call services supplied by the firmware.
`\#![no_main]` disables Rust's usual startup path, and the `uefi` crate's `#[entry]` macro generates the entry wrapper required by UEFI:

[source,rust]
----
#![no_main]
#![no_std]

use uefi::{entry, Status};

extern crate alloc;

#[entry]
fn main() -> Status {
    // A UEFI entry point must return a status or keep control indefinitely.
    loop { core::hint::spin_loop(); }
}
----

This is already a bootable loader: reaching the loop proves that the firmware found the file and entered Rust code.
The crate enables the `global_allocator`, `alloc`, and `panic_handler` features of `uefi`.
Consequently, collections such as `Vec` are available while UEFI boot services remain active; neither the allocator nor other boot services may be used after `ExitBootServices`.

=== Building a Diagnostic Path

Before loading a kernel, Telos establishes a way to display progress and errors.
That path has three dependencies, introduced in the order in which they are needed:

. read the font file from the same boot volume as the loader;
. acquire a writable framebuffer from UEFI's Graphics Output Protocol (GOP); and
. combine both resources in a framebuffer-backed logger.

=== Reading Files from the Boot Volume

The disk image places `font.psf` and `kernel.elf` in the filesystem root.
Instead of searching every disk, the helper asks UEFI for the filesystem from which the current loader image was started:

[source,rust]
----
pub(crate) fn get_file_data(filename: &'static str) -> Result<Vec<u8>> {
    // Open the volume that contains this loader image.
    let fs: ScopedProtocol<SimpleFileSystem> =
        boot::get_image_file_system(boot::image_handle())?;
    let mut fs = FileSystem::new(fs);

    // UEFI file APIs use null-terminated UTF-16 paths.
    let path = CString16::try_from(filename)?;
    Ok(fs.read(path.as_ref())?)
}
----

`ScopedProtocol` closes the opened protocol when its wrapper leaves scope.
The returned `Vec<u8>` owns a copy of the file contents, so it does not borrow that protocol; it does, however, still use the UEFI-backed allocator.
The font parser uses this helper now, and the ELF loader can reuse it later.

=== Acquiring the Framebuffer

The Graphics Output Protocol is UEFI's interface to the display.
Among other operations, GOP exposes a https://wiki.osdev.org/Drawing_In_a_Linear_Framebuffer[linear framebuffer]: a region of memory whose bytes represent screen pixels.
Its mode information describes the resolution, scan-line stride, and pixel format, while its framebuffer object supplies the address and byte length.
The loader opens GOP and obtains the information that the `framebuf` dependency needs:

[source,rust]
----
pub(crate) fn initialize_framebuffer() -> Result<RawFrameBuffer> {
    // GOP describes the firmware-selected display mode and its backing memory.
    let handle = boot::get_handle_for_protocol::<gop::GraphicsOutput>()?;
    let mut gop = boot::open_protocol_exclusive::<gop::GraphicsOutput>(handle)?;

    let gop_mode = gop.current_mode_info();
    let gop_fb_size = gop.frame_buffer().size();
    let (format, bpp) = match gop_mode.pixel_format() {
        gop::PixelFormat::Rgb => (framebuf::raw::PixelFormat::Rgb32bit, 4),
        gop::PixelFormat::Bgr => (framebuf::raw::PixelFormat::Bgr32bit, 4),
        gop::PixelFormat::Bitmask => unimplemented!(),
        gop::PixelFormat::BltOnly => unimplemented!(),
    };

    Ok(unsafe {
        // SAFETY: GOP supplies the pointer, length, and display-mode metadata.
        RawFrameBuffer::new(
            gop.frame_buffer().as_mut_ptr(),
            gop_fb_size,
            gop_mode.resolution().0,
            gop_mode.resolution().1,
            gop_mode.stride(),
            format,
            bpp,
        )
    })
}
----

After this handoff, `framebuf` handles the low-level graphics operations.
Their internals are beyond this short introduction; the OSDev Wiki provides further material on https://wiki.osdev.org/GOP[GOP], https://wiki.osdev.org/Drawing_In_a_Linear_Framebuffer[framebuffer drawing], and https://wiki.osdev.org/PC_Screen_Font[PC Screen Fonts].

=== PSF and Early Text Output

Text output also requires glyph shapes, which PC Screen Font (PSF) stores as a header followed by fixed-size bitmaps.
PSF1 uses a small header and 8-pixel-wide glyphs; PSF2 records each dimension explicitly, and their magic values distinguish the versions.

`parse_psf_font` first reads the file into a temporary `Vec`, identifies its version by the header magic, and checks that all declared glyph data is present.
It then copies the validated header and glyphs into page-based storage, the below snippet illustrates parsing for PSF1 fonts, PSF2 handling is almost identical:

[source,rust]
----
if magic == PSF1_MAGIC {
    let header = unsafe {
        // File data is not guaranteed to have the header's alignment.
        (font_data_ptr as *const PSF1Header).read_unaligned()
    };
    let glyph_count = if header.font_mode & 1 != 0 { 512 } else { 256 };
    let glyph_size = glyph_count * header.character_size as usize;
    let total_size = size_of::<PSF1Header>() + glyph_size;

    if font_data.len() < total_size {
        return Err(PsfParseError::InsufficientDataForPSF1.into());
    }

    // Allocate enough whole pages for the persistent font copy.
    let page_count = total_size.div_ceil(PAGE_SIZE);
    let font_address = boot::allocate_pages(
        boot::AllocateType::AnyPages,
        MemoryType::LOADER_DATA,
        page_count,
    )?;

    unsafe {
        // Both ranges are valid for total_size bytes and do not overlap.
        core::ptr::copy_nonoverlapping(
            font_data_ptr,
            font_address.as_ptr(),
            total_size,
        );
    }

    let glyphs = unsafe { font_address.as_ptr().add(size_of::<PSF1Header>()) };
    Ok(unsafe { RawFont::new(Header::V1(header), glyphs, glyph_count) })
}
----

https://uefi.org/specs/UEFI/2.10_A/07_Services_Boot_Services.html[`allocate_pages`] asks UEFI boot services for whole 4 KiB physical pages.
The size is rounded up because UEFI allocates pages rather than individual bytes, and `AnyPages` allows the firmware to choose a suitable physical address.
After allocation, the parser copies the validated font into this range, so the temporary `Vec` may be dropped.

`MemoryType::LOADER_DATA` records in the UEFI memory map that these pages contain loader-owned data.
It does not keep them permanently reserved: after `ExitBootServices`, memory ownership passes to the operating system, whose physical-memory manager must preserve the font pages while they remain in use.

=== Putting the Pieces Together

File access, GOP, and PSF parsing now give `main` everything required for early text output.
The loader clears the framebuffer, records the range that a later page-table implementation must preserve, and registers the writer as the global logger:

[source,rust]
----
#[entry]
fn main() -> Status {
    let fb = graphics::initialize_framebuffer().unwrap();
    fb.fill(color::BACKGROUND);

    // Retain the range that the kernel's page tables must map later.
    let fb_addr = fb.ptr() as *mut u8 as u64;
    let fb_page_num = fb.ptr().len().div_ceil(PAGE_SIZE);

    let font = graphics::parse_psf_font(PSF_FILE_NAME).unwrap();
    let writer = RawWriter::new(font, fb, color::INFO, color::BACKGROUND);
    Logger::init(writer);

    info!("Hello World!!");
    debug!("Framebuffer: address: {fb_addr:#x}, number of pages: {fb_page_num:#x}");

    // Kernel loading is the next stage; stop here for this milestone.
    loop { core::hint::spin_loop(); }
}
----

=== Error Handling

Loader helpers return a shared `Result` whose `LoaderError` variants cover UEFI, filesystem, string-conversion, and PSF failures.

[source,rust]
----
pub(crate) type Result<T> = core::result::Result<T, LoaderError>;

#[derive(Debug, thiserror::Error)]
pub(crate) enum LoaderError {
    #[error("Uefi error: {0}")]
    Uefi(#[from] uefi::Error),
    #[error("Fs error: {0}")]
    UefiFs(#[from] uefi::fs::Error),
    #[error("FromStr error: {0}")]
    UefiFromStr(#[from] uefi::data_types::FromStrError),
    #[error("Psf error: {0}")]
    Psf(#[from] PsfParseError),
}
----

Each `#[from]` annotation generates a conversion into `LoaderError`, allowing the `?` operator to pass errors back to the caller without hiding their cause.
For this bring-up milestone, `main` uses `unwrap`, turning initialization failures into panics; a production loader should instead report the error through an available console and halt cleanly.
