Before the kernel can run, the machine needs to be brought into a known, usable state: memory must be mapped, hardware initialized, and the kernel image located and loaded into memory.
On a UEFI system this work falls to the bootloader: A small program that the firmware loads first and that runs with full access to UEFI boot services.
Once the loader has finished its setup, it hands control to the kernel and exits boot services, after which UEFI's runtime environment is no longer available.

Separating this early-boot work into a dedicated loader crate keeps the kernel itself free from UEFI dependencies entirely.
The kernel can then be compiled for a bare custom target with no assumptions about the environment.

=== Entry Point

The `uefi` crate's `#[entry]` macro takes care of the low-level ABI that UEFI expects from an application, exposing a clean Rust function as the entry point.
`extern crate alloc` pulls in the allocator that the uefi `global_allocator` feature provides, making heap allocation available from the start.

[source,rust]
----
#![no_main]
#![no_std]

use framebuf::{color, logger::Logger, raw::write::RawWriter};
use log::{debug, info};
use uefi::{boot::PAGE_SIZE, entry, Status};

extern crate alloc;

mod error;
mod file;
mod graphics;

const PSF_FILE_NAME: &str = "font.psf";

#[entry]
fn main() -> Status {
    let fb = graphics::initialize_framebuffer().unwrap();
    fb.fill(color::BACKGROUND);

    let fb_addr = fb.ptr() as *mut u8 as u64;
    let fb_page_num = fb.ptr().len().div_ceil(PAGE_SIZE);

    let font = graphics::parse_psf_font(PSF_FILE_NAME).unwrap();

    let writer = RawWriter::new(font, fb, color::INFO, color::BACKGROUND);

    Logger::init(writer);

    info!("Hello World!!");
    debug!("Framebuffer: address: {fb_addr:#x}, number of pages: {fb_page_num:#x}");

    loop {}
}
----

The `uefi` dependency is configured with the `global_allocator`, `alloc`, and `panic_handler` features, so heap allocation and panics are handled without any explicit setup code:

[source,toml]
----
[dependencies]
uefi = { version = "0.37", features = [
    "global_allocator",
    "alloc",
    "panic_handler",
] }
log.workspace = true
----

=== Boot Stages

The loader currently performs the following steps in sequence:

1. Acquire the GOP framebuffer and clear it to the background color.
2. Read `font.psf` from the EFI filesystem and parse it into persistent memory.
3. Register a `RawWriter` as the global logger so `log` macros render text to the screen.

Kernel loading and handoff are not yet implemented.

=== Error Handling

The loader defines a unified error type that wraps the various UEFI and parsing failures that can occur:

[source,rust]
----
pub(crate) type Result<T> = core::result::Result<T, LoaderError>;

#[derive(Debug, thiserror::Error)]
pub(crate) enum LoaderError {
    #[error("Uefi error: {0}")]
    Uefi(#[from] uefi::Error),
    #[error("Fs error: {0}")]
    UefiFs(#[from] uefi::fs::Error),
    #[error("FromStr error: {0}")]
    UefiFromStr(#[from] uefi::data_types::FromStrError),
    #[error("Invalid filename: {0}")]
    InvalidFile(&'static str),
    #[error("Psf error: {0}")]
    Psf(#[from] PsfParseError),
}
----

`thiserror` works in `no_std` contexts and generates `From` impls for each variant, so the `?` operator propagates errors across the loader without manual conversions.

=== File I/O

UEFI exposes the EFI System Partition through the `SimpleFileSystem` protocol.
The `file` module wraps this into a single helper that returns file contents as a heap-allocated byte vector:

[source,rust]
----
pub(crate) fn get_file_data(filename: &'static str) -> Result<Vec<u8>> {
    let fs: ScopedProtocol<SimpleFileSystem> =
        boot::get_image_file_system(boot::image_handle())?;
    let mut fs = FileSystem::new(fs);

    let path = CString16::try_from(filename)?;
    Ok(fs.read(path.as_ref())?)
}
----

`boot::get_image_file_system` returns the filesystem the loader was launched from — the EFI System Partition.
The filename is converted to `CString16`, the wide-character format UEFI requires, before being passed to `fs.read`.

=== Graphics

The first thing the loader does is take control of the framebuffer.
This must happen while UEFI boot services are still active, because the GOP handle and the filesystem used to load the font are both unavailable after `exit_boot_services`.
The `framebuf` crate provides a raw framebuffer abstraction and a character renderer backed by PSF bitmap fonts.
All framebuffer and font work is in the `graphics` module.

==== Framebuffer Initialization

UEFI exposes the display through the Graphics Output Protocol (GOP).
The loader acquires an exclusive handle to it and extracts the framebuffer pointer and mode information:

[source,rust]
----
pub(crate) fn initialize_framebuffer() -> Result<RawFrameBuffer> {
    let handle = boot::get_handle_for_protocol::<gop::GraphicsOutput>()?;
    let mut gop = boot::open_protocol_exclusive::<gop::GraphicsOutput>(handle)?;

    let gop_mode = gop.current_mode_info();
    let gop_fb_size = gop.frame_buffer().size();
    let (format, bpp) = match gop_mode.pixel_format() {
        gop::PixelFormat::Rgb => (framebuf::raw::PixelFormat::Rgb32bit, 4),
        gop::PixelFormat::Bgr => (framebuf::raw::PixelFormat::Bgr32bit, 4),
        _ => unimplemented!(),
    };

    Ok(unsafe {
        RawFrameBuffer::new(
            gop.frame_buffer().as_mut_ptr(),
            gop_fb_size,
            gop_mode.resolution().0,
            gop_mode.resolution().1,
            gop_mode.stride(),
            format,
            bpp,
        )
    })
}
----

GOP reports pixels as either RGB or BGR depending on the hardware; this is mapped to the matching `PixelFormat` variant so the `framebuf` crate writes colors correctly.
Once the `RawFrameBuffer` is constructed the loader immediately fills it with the background color, erasing any firmware output that was on screen.

==== PSF Fonts

PC Screen Font (PSF) is a simple bitmap font format: a small header followed by a contiguous array of fixed-size glyph bitmaps, one bit per pixel, row by row.
It comes in two versions distinguished by their magic number.

PSF1 (magic `0x0436`) has a four-byte header:

[cols="1,1,3"]
|===
|Field |Type |Description

|`magic`
|`u16`
|`0x0436`

|`font_mode`
|`u8`
|`0` for 256 glyphs, `1` for 512 glyphs

|`character_size`
|`u8`
|Glyph height in bytes; width is always 8 pixels
|===

PSF2 (magic `0x864ab572`) carries a richer 32-byte header with explicit dimensions:

[cols="1,1,3"]
|===
|Field |Type |Description

|`magic`
|`u32`
|`0x864ab572`

|`version`
|`u32`
|Currently always `0`

|`header_size`
|`u32`
|Header size in bytes (usually 32)

|`flags`
|`u32`
|Non-zero if a Unicode table follows the glyphs

|`length`
|`u32`
|Number of glyphs

|`glyph_size`
|`u32`
|Bytes per glyph

|`height`
|`u32`
|Glyph height in pixels

|`width`
|`u32`
|Glyph width in pixels
|===

The glyph bitmap data follows immediately after the header in both versions.

`parse_psf_font` reads the font file via `get_file_data`, inspects the first bytes to determine the version, validates that the buffer is large enough to contain both the header and all glyph data, then copies everything into pages allocated with `MemoryType::LOADER_DATA`:

[source,rust]
----
let page_count = total_size.div_ceil(PAGE_SIZE);
let font_address = boot::allocate_pages(
    boot::AllocateType::AnyPages,
    MemoryType::LOADER_DATA,
    page_count,
)?;
----

`LOADER_DATA` pages survive `exit_boot_services`, so the font remains accessible once the kernel takes over.
After the copy, a `RawFont` value is constructed from the header variant, a pointer to the glyph buffer, and the glyph count.

==== Logger

With the framebuffer and font ready, a `RawWriter` is built from them and registered as the global `log` logger:

[source,rust]
----
let writer = RawWriter::new(font, fb, color::INFO, color::BACKGROUND);
Logger::init(writer);
----

After this point, standard `log` macros (`info!`, `debug!`, etc.) render text directly to the framebuffer.
The two color arguments set the foreground and background used for all subsequent text output.
