Telos separates the boot process into three Rust crates.
The `loader` crate is the program started by UEFI, `kernel` is the program to which it eventually transfers control, and `framebuf` is a dependency crate that handles low-level graphics.
Keeping these responsibilities separate also lets the loader and kernel use different compilation targets.
Only the files relevant to this paper are shown below:

[source]
----
telos/
├── .cargo/config.toml
├── framebuf/
├── kernel/
│   ├── src/main.rs
│   └── x86_64-unknown-telos.json
├── loader/src/
│   ├── file/mod.rs
│   ├── graphics.rs
│   └── main.rs
├── nix/
└── psf/light16.psf
----

=== Toolchain and Targets

The supplied Nix flake provides a reproducible toolchain as well as OVMF, QEMU, and the utilities needed to create a disk image.
It exposes the following development commands:

[source,sh]
----
nix build .#loader     # build the UEFI application
nix build .#kernel     # build the freestanding ELF kernel
nix build .#bootimage  # assemble the FAT boot image
nix run                # build and run the image with QEMU/OVMF
nix develop            # open the development environment
----

The two programs require different targets because they run in different environments.
The loader uses Rust's built-in `x86_64-unknown-uefi` target, which produces a PE32+ executable that UEFI can start directly.
The kernel has no firmware or operating-system runtime to target, so `x86_64-unknown-telos.json` describes its bare-metal environment.
The linker uses its default memory layout and `_start` as the entry point; no custom linker script is needed.

The workspace also rebuilds `core`, `alloc`, and the compiler built-ins through `.cargo/config.toml`.
This currently requires a nightly compiler with the Rust sources installed.

Inside `nix develop`, the equivalent direct Cargo commands are:

[source,sh]
----
cargo build -p loader --target x86_64-unknown-uefi
cargo build -p kernel -Zjson-target-spec \
  --target kernel/x86_64-unknown-telos.json
----

=== Kernel Stub

At this stage the kernel only needs to prove that it can be linked with the expected entry symbol.
It cannot use Rust's standard library because no operating system exists underneath it, and it cannot return because there is no caller to resume.
The https://wiki.osdev.org/System_V_ABI[System V AMD64 calling convention] gives the loader and kernel an explicit agreement about how a later function argument will be passed:

[source,rust]
----
#![no_std]
#![no_main]

// Do not mangle `_start`: the linker looks for this exact symbol name.
#[unsafe(no_mangle)]
pub extern "sysv64" fn _start() -> ! {
    // There is nowhere to return to until the kernel implements shutdown.
    loop { core::hint::spin_loop(); }
}
----

Later, `_start` will accept a pointer to the boot information described in the next chapter.

=== Boot Image and QEMU

Building the two executables is not enough: the firmware must also be able to find the loader, and the loader must be able to find its input files.
For removable x86-64 media, UEFI looks for the fallback path `\EFI\BOOT\BOOTX64.EFI` on a FAT filesystem.
`nix/img.nix` creates that filesystem and copies in the kernel and font:

[source]
----
boot.img (FAT32)
├── efi/boot/bootx64.efi
├── kernel.elf
└── font.psf
----

`nix run` attaches this image to QEMU and uses OVMF as the UEFI firmware.
It writes serial output to `stdio.log` and CPU-event diagnostics to `qemu.log`, making failures that would simply freeze a physical machine reproducible and inspectable.
