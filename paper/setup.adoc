Telos is a Cargo workspace with three crates.
`loader` is the UEFI application, `kernel` is the freestanding destination, and `framebuf` is a drawing dependency used for early output.
The boot image additionally contains `font.psf` and `kernel.elf`:

[source]
----
telos/
├── .cargo/config.toml
├── framebuf/
├── kernel/
│   ├── linker.ld
│   ├── src/main.rs
│   └── x86_64-unknown-telos.json
├── loader/src/
│   ├── file/mod.rs
│   ├── graphics.rs
│   └── main.rs
├── nix/
└── psf/light16.psf
----

=== Toolchain and Targets

The supplied Nix flake is the reproducible path used for the project.
It provides Rust, the UEFI target, OVMF, QEMU, and the image-building utilities:

[source,sh]
----
nix build .#loader     # build the UEFI application
nix build .#kernel     # build the freestanding ELF kernel
nix build .#bootimage  # assemble the FAT boot image
nix run                # build and run the image with QEMU/OVMF
nix develop            # open the development environment
----

The loader uses Rust's standard `x86_64-unknown-uefi` target.
The kernel instead uses `x86_64-unknown-telos.json`, which is used to compile the kernel to a bootable image with a custom linker script applied.
The workspace's `.cargo/config.toml` rebuilds `core`, `alloc`, and compiler built-ins, so the build currently requires a nightly compiler and Rust sources.

The two direct Cargo commands are:

[source,sh]
----
cargo +nightly build -p loader --target x86_64-unknown-uefi
cargo +nightly build -p kernel -Zjson-target-spec \
  --target kernel/x86_64-unknown-telos.json
----

=== Kernel Stub

The kernel deliberately does nothing except provide the symbol used as the handoff target:

[source,rust]
----
#![no_std]
#![no_main]

#[unsafe(no_mangle)]
pub extern "sysv64" fn _start() -> ! {
    loop {}
}
----

Later on, it will receive a pointer to boot information passed to it by the bootloader.

=== Boot Image and QEMU

UEFI removable-media boot expects a FAT filesystem containing the architecture-specific fallback path.
`nix/img.nix` produces the relevant layout:

[source]
----
boot.img (FAT32)
├── efi/boot/bootx64.efi
├── kernel.elf
└── font.psf
----

`nix run` starts QEMU with OVMF code and variable images, attaches `boot.img`, and writes serial and CPU-event logs to `stdio.log` and `qemu.log`.
OVMF follows the same UEFI interfaces as a physical machine, while QEMU makes early faults reproducible and inspectable.
